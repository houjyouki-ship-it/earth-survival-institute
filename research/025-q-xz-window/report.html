問い

024 は、RAM の小さい狙い撃ち読取装置（T2 の手引きから作る光電読取＋真空管論理）が届ける、機械読み層の価値の割合 q を根拠なく 0.3 と置いた。ΔV は q にほぼ比例する。本回は GitHub Arctic Code Vault の実際の構成から q(M) を推定した。

事実入力（本回の前半＝第25回前段で開いて確認、写しは sources/）

  • 【事実（Arctic Vault）】2020-02-02 のスナップショットは既定ブランチの HEAD、100KB 超のバイナリは除外（250星以上は保持）、repo ごとに1つの TAR、21TB、186 リール。
  • 【事実（GUIDE.md）】外側 TAR に非圧縮の META、圧縮された COMMITS、repo.tar.xz。圧縮は XZ（LZMA）。Tech Tree は「非圧縮・非符号化の人が読めるリール」。リール数は 188（ガイド1＋データ187）と書かれており、Arctic Vault ページの 186 と食い違う。
  • 【事実（xz 形式仕様、liblzma ソース lzma_common.h：LITERAL_CODER_SIZE 0x300）】リテラル確率表は 0x300<<(lc+lp) 個。xz -6 の辞書は 8 MiB。
  • 【事実（Wikipedia：EDSAC、Whirlwind I、IBM 704）】EDSAC は1952年まで 512×18ビット、Whirlwind は 2048×16ビットの設計、IBM 704 は 4096×36ビット＝18,432 バイト級。

方法

  • 展開に要る RAM：R = S0 + min(D, S_tar)。S0=16 KiB（確率表 12 KiB＋状態【推測】）、D=8 MiB（xz -6）。S_tar は 2020-02-02 以前の最後のコミットの木から TAR の大きさを再構成（250星未満は 100KB 超のバイナリ拡張子を除く。拡張子判定は【推測】の近似）。
  • 標本：高層（現在の星≥250、6区間×35件＝210件）、低層 low0（0星、2019-11-13〜2020-02-01 作成、50件）、low1（1〜249星、1年以内作成、70件）。重みは星・repo 数・非圧縮バイト。2000回のブートストラップ。
  • 圧縮部分標本：大きさで層化した30件の実 tarball を LZMA2 辞書 4 KiB〜8 MiB で圧縮。
  • 024 のモデル（同じ乱数系列）に q(M) を入れ、読取装置の RAM を4つのシナリオで回した。

主要結果

  • 【独自推定】高層・星重みの q(M)：IBM 704 級（18 KiB）0.005［0, 0.014］、64 KiB 0.056［0.029, 0.088］、144 KiB 0.17［0.12, 0.23］、1 MiB 0.43［0.36, 0.51］、9 MiB で 1.0。
  • 低層 low1（repo 数重み）：64 KiB 0.20［0.12, 0.30］、1 MiB 0.70。low0：18 KiB で 0.11、64 KiB で 0.61。バイト重みでは 1 MiB でも 0.01〜0.11（大きい repo がバイトの大半）。
  • TAR の大きさの中央値：高層 1.15 MB、low1 0.31 MB、low0 20 KB。木から推定した TAR と実 TAR の比の中央値 0.957。
  • 辞書の費用（部分標本30件、合計 187 MB）：8 MiB 比で 64 KiB は +29%、1 MiB は +18%、4 KiB は +38%。ただし repo ごとの中央値は +3%（p90 +19%）で、合計は重複の多い数件（例：講義資料 repo は 8 MiB で 17.9 MB、64 KiB で 34.2 MB）が支配する。
  • ΔV（024 の主設定 m23=943、T1 板に手引き）：
  • 読取 RAM 4 KiB〜144 KiB（Whirlwind〜704 拡張級）：平均 q 0.037、ΔV=0.012（024 の 0.093 の約1/8）。
  • 同じ RAM で、運営者が辞書 64 KiB で再圧縮していた場合：q 0.18、ΔV=0.055。
  • 144 KiB〜1 MiB：q 0.29、ΔV 0.089（024 の仮定 q=0.3 とほぼ同じ）。再圧縮なら q=1.0、ΔV 0.31。
  • 128 B〜1152 B（Baby〜EDSAC 級）：q=0、ΔV=0。

仮説の判定

  • H37a（高層星重み q(64 KiB)<0.10）：支持（0.056）。
  • H37b（低層 repo 重み q(64 KiB)≥0.30）：棄却（low1 0.20。low0 は 0.61 だが両方の条件）。
  • H37c（18 KiB で全層・全重み q<0.05）：棄却（low0 repo 重みが 0.11。0星の極小 repo のみ。星重みは 0.005 で実質支持）。
  • H37d（辞書 64 KiB の費用 <15%）：棄却（合計 +29%。repo 中央値 +3% なら成り立つが、登録は合計）。
  • H37e（4〜144 KiB の読者で ΔV(板)<0.03）：支持（0.012）。
  • H37f（高層星重み q(1 MiB)≥0.30）：支持（0.43）。

批判的検討（限界）

  • 星は 2026 年の値で、2020 年の値ではない。削除された repo は標本に入らない（生存バイアス）。星重みは「価値」の代理にすぎない【推測】。
  • 区間内では「ランダムな作成月→ランダムなページ→最大3件」で選んだので、区間内の抽出確率は等しくない（collect.py に記録した逸脱：1件→最大3件/検索）。区間の重みは今の total_count。
  • R は「出力をテープに流し、窓だけ RAM に置く」前提の下限。逆に、遅いランダムアクセスの補助記憶（ドラムなど）に窓を置ければ、時間と引き換えに q は上がる【推測】。処理速度は入れていない。
  • 部分標本は30件で、H37d の合計は数件に左右される。

結論

024 の q=0.3 は「読取装置の RAM が 144 KiB〜1 MiB」の場合にだけ当たる。1950年代前半級（4〜144 KiB）の読者には、Arctic Vault の repo.tar.xz（8 MiB 辞書）は星重みで約4%しか開けず、手引きの価値は 024 の約1/8 になる。壁は計算力ではなく XZ の辞書の大きさで、辞書を 64 KiB にすれば同じ読者で q が約5倍（0.037→0.18）になる。その費用は repo 中央値で +3%、合計で +29%。

誰が何を変えるべきか

  • アーカイブ運営者（GitHub Archive Program、Piql など）：次の預け入れでは、少なくとも Tech Tree が索引する重要 repo を 小さい辞書（≤64 KiB、例：xz --lzma2=dict=64KiB）で圧縮した版か非圧縮版を別に書く。全体を再圧縮すると約3割増だが、重要 repo だけなら費用は小さい【推測】。
  • 各リールの索引に、ファイルごとの「展開に要る窓の大きさ」を人が読める形で書く（xz の Index には非圧縮サイズしかなく、辞書の大きさはブロックヘッダを読まないと分からない）。
  • 024 の提言（製作手引きを板に）は維持するが、その価値は手引きの読取装置が ≥1 MiB 級の RAM を作れるかで約8倍変わる。手引きに「RAM を増やす」章（磁気コア）を入れる意味がある。
