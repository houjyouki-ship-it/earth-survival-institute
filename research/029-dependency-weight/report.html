問い

028 は「星の数」を repo の価値とみなし、0.1 リールの欲張り選択が星順の2.8倍効くと出したが、選ばれたのは一覧や教材だった。価値を「どれだけ多くの repo がそれに依存しているか」で測ると、重要 repo の割合、選ばれる集合、q・ΔV はどう変わるか。

事実入力（本回開いて確認）

  • 【事実（ecosyste.ms Packages API の OpenAPI 定義、sources/packages_openapi.yaml）】/packages/lookup は repository_url で package を引き、dependent_repos_count・dependent_packages_count を返す。sort 引数に dependent_repos_count が使える。匿名の上限は 5,000/時（応答ヘッダー）。
  • 【事実（同 API の応答、本回）】例：psf/requests の最大 package は pypi:requests で dependent_repos_count 679,836（sources/lookup_psf_requests_example.json）。

方法

  • 対象：028 の items（≥20,000 星の全数 1,339件と、025 標本の高層 175件、区間の重み w つき）。

批判的検討（限界）

  • 依存数は npm の大きさに引っ張られ（94%）、生態系の間で比べられない。生態系ごとに総量をそろえると ≥20,000 星の割合は 6.6%→53% に変わる。どちらも「回復に役立つ度合い」の代わりとしては弱い【推測】。
  • lookup は repository_url の一致で引くので、名前の偶然一致（linux の bower 版など）や、改名した repo の取りこぼしがありうる。D1 は最大値なので、偶然一致で小さな値が付く影響は小さい。
  • 依存重みは裾が極端に重く、区間重み w の大きい標本1件が全体を決めた。高層全体の割合や、0.1 リールの予算つき選択の評価は、この1件の有無で大きく動く。決めるには依存の上位の全数調査が要る（open_problems 90）。
  • 2026 年の依存数を使った。2020 年の収蔵時とはずれる。
  • 修正：sim.py の q 計算で、全重みが二重書きされたとき 0/0 になる不具合を初回実行後に直した（予算 1 リールの値だけに影響し、判定には使っていない）。

結論

星と依存数は ≥20,000 星の repo の間でほぼ無相関（ρ 0.02）で、予算が小さいほど選ばれる repo が入れ替わる（0.003 リールで Jaccard 0.22）。損失は非対称で、依存数だけで選ぶと星で測った価値の約4分の3を失う。星で選んだ場合に依存で測って失う分はそれより小さい（0.003 リールで約4割）。依存数だけで選ぶのは危うい。linux、cpython、bitcoin、hadoop のような基盤がほぼ0と数えられるからである。2つを正規化して半々に混ぜると、どちらで測っても最適の91%以上が得られる。高層全体を c4 で書けば（約4 リール）、q は重みによらず 0.76 で、選び方の問題そのものが消える。依存で測った重要 repo の割合は、標本の裾が重すぎて今のデータでは決まらない。

誰が何を変えるべきか

  • Tech Tree の索引担当とアーカイブ運営者：小窓版を 0.03 リール（約3.4 GB）未満の予算で選ぶなら、星と依存数の正規化重みを半々に混ぜて選ぶ（どちらで測っても損失は9%未満）。依存数だけでは選ばない（OS・処理系・基盤ソフトが抜ける）。0.13 リールあれば ≥20,000 星の全数、約4 リールあれば高層全体を書けば、重みの議論は要らない。028 の提言（高層全体を c4 で）は重みを変えても成り立つので維持する。
  • 本研究所：依存重みでの母集団の推定には、標本ではなく依存の上位の全数調査を使う。
