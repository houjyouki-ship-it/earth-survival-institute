研究019：手で読めるアーカイブ書式 — Piql の実書式は人手で読めるか（open_problems 62・63）

問い

018 は「Piql の非圧縮データは顕微鏡＋人手で 0.37人年/MB で読める実質 T2 媒体」とした。ただし、データ部分をそのまま読める（攪拌なし・組織的符号）と仮定していた。本回は Piql の公開ソースで実際の書式を確かめ、(1) その書式を人手で読む費用、(2) 手読み向けに設計した書式の費用と残留誤り、(3) フィルム面積の費用、を比べた。

  • RS の実装：GF(256)（多項式 285）の RS(255,207) を自前で実装し、符号化→誤り注入→復号（Berlekamp–Massey、Chien 探索、Forney）を300符号語×5条件で行い、GF 乗除算の回数を数えた。検査（48シンドローム）だけで1符号語 12,192回、誤り10個の訂正込みで約 28,500回。
  • 手読み書式（1 MB のデータを実際に符号化・誤り注入・復号）：A1 生データ 1ビット/画素・二重読み、A2 離れた3複製（2本を読み、食い違えば3本目で多数決）、A3 ハミング(7,4)・1回読み、A3i 符号語の7ビットを離れた7帯に置くハミング。
  • 誤りのモデル：フィルムの独立画素誤り p∈[1e-5, 1e-2]、バースト（画素割合 1e-3、平均長100画素、区間内は確率0.5で反転）。1回読みの読み誤り 5.5e-4（[1e-4, 3e-3] の幾何中心）、二重読みの残留はその1/10、4階調の読み誤りは2値の3倍【すべて推測】。

主な数値

  • Piql の実書式は 018 の想定より桁違いに手読みが重い。費用の内訳（データ1バイトあたり秒の中央値）は、4階調の二重読み 4.4、攪拌解除 8.4、2段の位置転記 15.4、RS 全シンドローム 3,763（データ1バイトあたり GF 乗算 72.6回）。
  • 攪拌は無視できない：攪拌後の GUIDE は印字可能文字が 37.9%（原文 99.99%）で、鍵ストリームを作らないと文字として読めない。ただし鍵は通常 key=1（GUIDE でもゼロ列でも1回目で通った）で、フレームごとに同じ鍵ストリームを使い回せる【推測：鍵の保存場所はメタデータと推定、未確認】。
  • 誤り訂正の効き目：Piql の連接 RS は、独立誤り p=1e-2 でも符号語の失敗が実質0（解析で 5.6e-16）、バーストでも内符号語あたりの誤りは最大4（訂正限界24）。機械で読むなら非常に頑健だが、その頑健さを手で得るには約600人年/MB かかる。
  • 手読み書式の残留誤り（p=1e-3）：生データ二重読み 8.4e-3、ハミング 9.3e-5、3複製 5.8e-5。RS を省いた Piql は 4.6e-3。
  • 費用：3複製 0.74人年/MB（生データ二重読みと同じ。3本目を読むのは0.3%だけ）、ハミング 2.80（14画素の読みより、24回の偶奇計算が重い）。1,000人年（100人×10年）で読める量は、3複製で約1,350 MB、RS を全検査する Piql で約1.6 MB。
  • 面積：Piql の最小線幅は 0.42 µm（1180 lp/mm）で、読むには NA≈0.65 が必要。線幅2倍なら NA 0.32、5倍なら 0.13。10 MB の3複製は線幅2倍で1リールの0.18%、5倍で1.13%。

批判的検討

  • 4kv6 が GitHub Archive の書式とは限らない【推測】：4kv11 は RS がやや軽い（内 24パリティ）が、攪拌と2段インターリーブは同じ。RS 全検査の費用は約半分になるだけで、桁は変わらない。
  • RS を省く読み方は、残留誤りが「読み誤り」で決まる（p=1e-5 でも 7e-4）。文章なら人が文脈で直せるが、仕様・数表・コードには足りない【推測】。
  • 人手の速度は推測のまま（open_problems 61）。ただし H31a の結論（RS 全検査で数百人年/MB）は、速度の幅の5% 点でも約210人年/MB で変わらない。
  • 3複製の境界：p=1e-3＋バーストでの 1.0e-4 は、別の種で 0.76〜1.12e-4 に揺れる。残留を1桁下げるには、5複製か、3複製＋行ごとの簡単な検査和が要る（本回は未検証）。
  • ハミングの費用はビット操作の速さに強く依存する：1回0.2〜2秒としたが、画素14個を読む時間だけで 018 の M-U（1バイト2.66秒）を超える。018 は Piql の 4.4画素/バイトを2値の速度で読むと仮定していたので、比較の基準そのものが楽観的だった。
  • 面積は効かない：H31e は僅差で棄却したが、1%強でも優先 10 MB のために1リールの1%を使うのは、費用として小さい【推測】。
  • 新規性：Piql の公開ソースから実際の符号化の連鎖（攪拌・2段インターリーブ・連接 RS）を読み取り、人手で読む費用を GF 演算の実数で数えたものは、確認した公開文献には見当たらない。018 の楽観（0.37人年/MB）を、実書式では 4.8〜640人年/MB に訂正した。

結論

018 の「Piql の非圧縮部分は実質 T2 媒体」は、実際の Piql 書式では成り立たない。攪拌・インターリーブ・連接 RS のため、誤りを検査しながら手で読むと約600人年/MB かかり、検査を省いても約5人年/MB で、残留誤りは 1e-3 級になる。一方、1ビット/画素・攪拌なし・離れた3複製の書式なら、費用は約0.7人年/MB、残留誤りは独立誤り p=1e-3 で 6e-5 になり、面積の追加は1リールの0.2〜1%で済む。手で読む層では、代数的な誤り訂正（RS・ハミング）より、複製と目視の照合のほうが安い。

この結果を受けて、誰が何を変えるべきか

  • Piql・GitHub Archive Program：手引き・書式仕様・重要文書の優先 1〜10 MB を、機械用の書式とは別に、攪拌なし・1ビット/画素・線幅を2倍以上にした3複製（リールの離れた位置に置く）で書き込むべきである。018 の提言（非圧縮で別に書く）だけでは足りず、Cipher と RS を外すことが要る。
  • 本研究所：018 の M-U（0.37人年/MB）を「手読み向け書式の場合」に限定し、Piql の実書式では 4.8（検査なし）〜640（全検査）人年/MB と併記する。
