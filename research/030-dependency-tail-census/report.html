問い

029 では 025 標本の1件（bestiejs/json3、区間重み 556）が高層の依存重みの86%を占め、≥20,000 星の repo の割合の90%区間が 2.4〜56% と決まらなかった。依存数の大きい repo を全数で数え、標本はそれ以外にだけ使うと、割合、q、予算つき選択はどう変わるか。

事実入力（本回開いて確認）

  • 【事実（ecosyste.ms registries 一覧、sources/registries_list.json）】registry は117件。npmjs.org の package 数 5,978,351、pypi.org 942,665 など。
  • 【事実（ecosyste.ms Packages API、029 の sources/packages_openapi.yaml）】/registries/{name}/packages は sort=dependent_repos_count で並べられる。per_page=1000 が使えた。応答の repo_metadata に星・作成日・fork・大きさがある。
  • 【事実（同 API の応答、sources/npm_top2_example.json）】npm の1位は supports-color（dependent_repos_count 5,765,200、repo chalk/supports-color の星 374）、2位は fs.realpath（5,532,257、星 25）。

方法

  • 各 registry で、dependent_repos_count の降順に、値が 1,000 未満になるまで取った（全117件で到達。打ち切りなし。終わったページの最後の値の最大は 952）。
  • package を GitHub repo にまとめ（repository_url）、D1 = 最大の dependent_repos_count。GraphQL で改名を解決し、星・作成日・fork を取った。
  • 全数層：高層（星 ≥250、2020-02-02 以前、fork でない）のうち、星 <20,000 で D1 ≥ T の repo（主設定 T=10,000：3,872件）。≥20,000 星は 028 の全数（D1 は 029 の値と全数の値の大きい方）。
  • 標本層：025 標本の高層175件のうち全数層に入らないもの。区間の重みを (N_b − 全数層の件数) / 残りの標本数 に付け直した。
  • 新しく加わる repo の TAR は、025 の210件の回帰（log TAR = 2.95 + 0.714·log 大きさ、R² 0.57、残差 SD 1.59）に残差を足して付けた（主）。探索で、上位1,000件と無作為150件の TAR を 025 と同じ規則で実測した。
  • 読者 B（RAM 4〜144 KiB）、ΔV の式、費用、設定 c4（4 KiB 辞書・lc0）は 028・029 と同じ。

主要結果

  • 【独自計測】方法の検証：029 の lookup で D1 ≥10,000 だった repo（≥20,000 星 282件、標本10件）は、**全部（292/292）**全数リストに見つかった。標本からの件数の推定（Σ w·1[D1≥T]）は 3,220件で、全数 3,872件の 0.83倍。
  • 【独自計測】全数層 3,872件は星の区間にほぼ均等に散らばる（250〜499星 813件、500〜999 746件、1k〜2k 702件、2k〜5k 783件、5k〜20k 826件）。依存の上位は supports-color（星 374、D1 577万）、fsevents（568、529万）、resolve、statuses、send、serve-static で、npm の小さな部品。

仮説の判定

  • H42a（全数リストの再現率 ≥90%）：支持（100%、292/292）。
  • H42b（≥20,000 星の割合の90%区間の幅 ≤10.7 ポイント）：支持（0.21 ポイント）。
  • H42c（≥20,000 星の割合 ≥15%）：棄却（8.2%）。029 の点推定 6.6% は外れていなかった。json3 の重みの過大は、裾の全数が本当に重いことでほぼ打ち消されていた。
  • H42d（裾の全数が依存重みの ≥50%）：支持（89.4%）。
  • H42e（依存重みの収蔵のままの q ≥ 星重みの2倍）：支持（2.3倍、実測 TAR の探索で 2.6倍）。ただし TAR を中央値で置くと 1.2倍で、頑健ではない。
  • H42f（c4・0.01 リールの依存の欲張りで q 増分 ≥0.5）：支持（0.654）。
  • H42g（半々の混合が 0.01・0.1 リールで両方の最適の ≥80%）：支持（0.867／0.967、0.985／0.989）。029 の H41g は全数補正後も成り立つ。0.003 リールでは星の側 77% で、規則の外ではわずかに下回る。

批判的検討（限界）

  • dependent_repos_count は、manifest や lockfile にその package が書かれた repo の数で、間接依存を含むと思われる【推測】。fsevents（macOS 専用の任意依存）が529万あるのはそのためと考えられ、「回復した社会で役立つ度合い」を過大に見せる。直接依存だけの数は API からは取れなかった。
  • 依存数は 2026 年の値、星も 2026 年の値。2020 年の収蔵時とはずれる。
  • 高層の外（星 <250）に、D1 ≥10,000 の依存重みの半分以上がある。照会しなかった repo の星は ecosyste.ms の値で、作成日と fork は確かめていない。これらが Arctic Vault の低層に実際に入っているかは確かめていない。
  • TAR の回帰は R² 0.57 で、収蔵のままの q（H42e）はこの置き方で 0.026〜0.084 動く。上位1,000件（裾の依存重みの約89%）は実測で置き換えたが、標本層と ≥20,000 星は 028 の値のまま。
  • 逸脱：TAR の実測（tools/measure_tar.py）は事前登録になく、判定には使っていない。

結論

依存の重い裾を全数で数えると、≥20,000 星の repo が高層の依存重みに占める割合は 8.2%（90%区間 8.1〜8.3%）に決まった。依存重みの89%は、星 250〜20,000 の約3,900件の小さな部品（主に npm）にある。価値を依存で測ると、選ぶべき集合は星とはほぼ別物になる。その一方で費用は非常に小さく、0.003 リール（約 340 MB）で、高層全体を小窓版で書いたときの依存の ΔV の88%が得られる。星と依存を半々に混ぜる 029 の選び方は、0.01 リール以上ならどちらで測っても最適の87%以上を保つ。依存で測る価値の半分以上は星 250 未満の repo にあり、高層だけを対象にした 028・029 の数え方からは抜けていた。

誰が何を変えるべきか

  • Tech Tree の索引担当とアーカイブ運営者：小窓版（dict=4KiB,lc=0）の最初の 0.003 リール（約 340 MB）には、パッケージ管理系の依存数の上位（D1 ≥10,000）の約2,200件を入れ、星の上位はその次に混ぜる。星 250 未満でも依存数の大きい repo（約4,600件、約 0.0025 リール）は高層の外にあるので、別に拾う。028 の「高層全体を c4 で（約4 リール）」は依存で測っても ΔV 0.236 で、そのまま維持する。
  • 本研究所：今後、依存重みを使う解析では、標本ではなくこの全数リスト（data/pkgs.jsonl、data/repos_gh.jsonl）を基点にする。

既存研究に対する新規性

029 は標本だけで依存重みを推定し、裾の1件で割合が決まらなかった。本回は117 registry すべての依存数の上位を 1,000 まで取って全数層を作り、標本を付け直した重みで推定した。その結果、割合を ±0.1 ポイントに決め、依存で測った価値の大半が星 250〜20,000 と星 250 未満の小さな部品にあること、その部品を小窓版で書く費用が 0.003 リール程度であることを示した。
