批判的検討

  • 依存側の a は未知でなくなった。npm の部品は被依存1件あたり月120回落とされ、download の割合で配ると典型的な部品は数百万台の機械にある。見つかる確率を事前登録の下限 10⁻³ のさらに 1/300（3×10⁻⁶）まで下げないと写しは足りなくならない。035 の事前分布 logU[10⁻⁵,10⁻²] は依存側では低すぎた。
  • その代わり、依存側の残りは g（パッケージで欠ける価値）が決める（Spearman 0.94）。npm の写しは公開された tarball で、履歴・試験・ビルド手順を欠くことがある。写しを無限にしても依存側 f_orph は 0.103 より下がらない。次の未知は a ではなく g（open_problems 107）である。
  • 星側は a の事前分布のまま。星重みの 57% は npm にも Debian にも Homebrew にも対応せず、その多くは一覧・教材（036）なので、download のような公開の写しの数がない。半々の a の Spearman −0.77 は、ほぼ星側から来る。GitHub は clone 数を公開しておらず、本研究は星側の a を測れていない。
  • 配り方の仮定：「機械×package の組を download の割合で配る」は、CI や鏡像の download が多い package ほど写しを多めに数える。ただし上限を機械の総数で切り、写しが数桁多い所で飽和しているので、この偏りが結論を変えるには写しを 1,000 分の1 以下に減らす必要がある【推測】。
  • 地域：download の地域の内訳は npm から公開されておらず、035 の s_r（開発者の地域の割合、推測）のまま。南半球 s=0.05〜0.10 でも λ は数百以上で飽和する。
  • 時間：Backblaze の AFR はデータセンターの HDD の値で、ノートPCの SSD や電源を切った保管には直接当てはまらない。t を 20 年にしても (1−0.0157)^20≈0.73 で、効きは小さい（Spearman 0.004）。
  • H49d・e の棄却は、主に星側が動かないことによる。依存側は予想どおり床に張りついたが、半々では星側が半分を占める。

結論

npm の公開 download 数から組み立てると、金庫の依存の重い部品の写しは典型的に数百万台の機械にあり、手元の写しが生き残り見つかる割合 a は約 0.01 で、035 の推測の範囲（10⁻⁵〜10⁻²）の上端を超える。依存側では写しの数は飽和しており、補えない割合は 0.106 で、パッケージで欠ける価値 g が決める。星側は公開の写しの数がない一覧・教材が多く、0.45→0.41 にしか下がらない。半々では f_orph 0.27、第2拠点が束を上回る確率は A_XPT_S で 0.41→0.33、A_XPT_E では 0.93 のままで、035・036 の読み替え（Ord では束が上、XPT では第2拠点がほぼ同等か上）は変わらない。

この結果を受けて、誰が何を変えるべきか

  • 南半球の第2拠点の運営者：依存の重い npm の部品の中身は手元の写しが十分あるので、第2拠点に置く必要は小さい。置くなら部品の履歴とビルド手順（tarball に入らないもの）と、配布系に載らない一覧・教材の repo を優先する。
  • 本研究所：a の事前分布を依存側では捨て、npm の項目は download からの λ を使う。次の主課題は g（open_problems 107）と、星側の文章型 repo の写しの数（星側の a）である。

既存研究に対する新規性

035・036 は a を推測の範囲で置いた。本研究は npm の公開 download 数（9,048 package、全数）で写しの数を下から数え、依存側では a が支配的な未知でなくなり、代わりにパッケージで欠ける価値 g が床を作ることを示した。確認した資料（Ord、XPT、Software Heritage、GitHub Archive Program、Debian、Homebrew、npm の文書）には、registry の download 数を崩壊後の知識保存の評価につなげたものは見当たらない。
