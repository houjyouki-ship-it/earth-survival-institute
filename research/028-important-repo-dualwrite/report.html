問い

025〜027 で、Arctic Vault の repo.tar.xz（辞書 8 MiB）は RAM 4〜144 KiB の読者には星重みで約4%しか開けず、読者側の工夫（テープ8台）でも高層全体に約1,200機械年かかると分かった。運営者側で重要 repo を小さい辞書で別に書くと、補助記憶なしの読者の q と ΔV はいくつになり、何リール増えるか。

事実入力（本回開いて確認）

  • 【事実（Arctic Vault、2026-10-17 取得の HTML、sources/arctic_vault_2026-10-17.html）】Featured projects は15件（dotnet/core、torvalds/linux、python/cpython、bitcoin/bitcoin、rails/rails、docker/machine、openssl/openssl、nodejs/node、Homebrew/brew、php/php-src、twbs/bootstrap、microsoft/TypeScript、apache/hadoop、Alamofire/Alamofire、v8/v8）。21TB を 186 リール。
  • 【事実（LZMA 仕様 lzma-specification.txt、026 で取得した写し）】確率配列 = 1846 + 768·2^(lc+lp) 個。lc を 3→0 にすると 10,752 B 減る。
  • 【事実（GitHub 検索 API、本回）】2020-02-02 より前に作られた非 fork・現在 ≥20,000 星の repo は 1,366 件。

方法

  • 母集団：高層（≥250 星）。≥20,000 星は全数（1,338 件で木を再構成、29 件はスナップショット前のコミットが取れず除外＝星 101 万、chromium/chromium は走査を中断し TAR=3 GB と置いた【推測】）、それ未満は 025 の標本（175 件）の重み。
  • 圧縮計測：Featured 15件＋≥20,000 星の無作為15件、合計 2.57 GB の実 TAR を、c0 8 MiB・lc3（収蔵時相当）、c1 64 KiB・lc3、c2 64 KiB・lc0、c3 16 KiB・lc0、c4 4 KiB・lc0 で圧縮。
  • need = S0(lc) + min(辞書, TAR)（S0：lc3 16 KiB、lc0 5.5 KiB）。非圧縮は 1 KiB【推測】。読者 RAM は logU[4 KiB, 144 KiB]。ΔV は 024 の式（板の手引き、m23=943）。

批判的検討（限界）

  • 64 KiB 辞書（025 の提言）は need 80 KiB で、4〜144 KiB の読者の16%しか届かない。辞書の大きさより先に、確率表（lc）と辞書の合計を読者の RAM より小さくすることが効く。025 の「64 KiB で再圧縮」という提言は弱すぎた。
  • 星は 2026 年の値。星は「人気」で、文明の回復に役立つ度合いではない。Featured（linux、cpython、openssl など基盤）は星ではわずか0.48%だが、実用の価値は大きいはず【推測】。欲張り選択の 2.8 倍は、この重みに強く依存する。
  • 費用の外挿は、計測30件の圧縮率をすべての repo に当てた。025 の30件では約2.4倍高くなり、どちらが代表的かは未確定。
  • 読者は補助記憶なしの B だけを扱った。027 のテープ読者（q 0.69）と組み合わせた場合は計算していない。
  • 逸脱：collect.py は chromium/chromium の木の再帰走査で API の上限を使い切りかけたため、03:07 UTC に止め、出力ログから census.json を再構成した（tools/census_from_log.py）。docker/machine は改名先 docker-archive-public/docker.machine で取得した。

結論

重要 repo の二重書きは安い。≥20,000 星の全数（1,337 件、高層の星重みの25%）を 4 KiB 辞書・lc0 で書いても約0.13 リール（186 リールの0.07%）で、補助記憶のない 1950 年代前半級の読者の q は 0.031→0.22、ΔV は 0.0096→0.068 になる。高層全体（約13万件）でも約4 リール（+2.2%）で q 0.76、ΔV 0.236 となり、024 が q=0.3 と仮定した値（0.093）を大きく超える。決め手は「辞書を小さく」だけでなく、「lc=0 で確率表を小さく」することで、その費用は +0.5% しかない。Featured15 だけを書く案は、星で測るとほぼ効果がない（q +0.004）。

誰が何を変えるべきか

  • アーカイブ運営者（GitHub Archive Program、Piql）：次の預け入れでは、少なくとも ≥250 星の高層全体を xz --lzma2=preset=6,dict=4KiB,lc=0,lp=0 相当で別に書く（約4 リール、圧縮率の不確実性で最大約10 リール）。予算が 0.1 リール級なら ≥20,000 星の全数を同じ設定で書く。025 の「64 KiB」は提言として弱いので置き換える。
  • Tech Tree の索引：重要 repo には「小窓版」の場所と、展開に要る RAM（4 KiB 辞書・lc0 で約 9.5 KiB）を書く。
  • 選ぶ基準：星順の欲張りは一覧や教材に偏るので、Tech Tree の担当者は依存関係（例：多くの repo が依存する基盤）で重みをつけ直すべき【推測】。重みに頑健なのは高層全体を書く案。

025 は辞書 64 KiB の費用を repo の小標本で測っただけで、重要 repo の大きさ分布、確率表の大きさ、読者の RAM 分布と費用の関係を扱っていなかった。本回は ≥20,000 星の全数と Featured の実 TAR から、設定ごとの費用（リール）と ΔV の関係を出し、「lc=0＋4 KiB 辞書で高層全体を約4 リール」という具体的で安い設定を示した。
